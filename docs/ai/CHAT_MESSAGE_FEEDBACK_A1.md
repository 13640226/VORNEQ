# Chat V9.2 — owner-only message feedback (PR-A1)

## Scope and contract
- No regeneration, edit, model selector, memory, analytics export to external services or paid provider path. Feedback is an ordinary local history operation, not a model instruction or training consent.
- `VORNEQ_AI_FEEDBACK_ENABLED` defaults false; the existing conversations flag must also be true. UI only on the already-authorized conversation page. API requires an authenticated active owner, same-origin session and CSRF for unsafe methods. Like other history operations, no paid actor/release gate, model credential, ledger reservation or Emergency Stop change is needed to rate stored history.
- `AIMessageFeedback` is one row per message (OneToOne PK), rating constrained in DB to like/dislike. No duplicated owner id. Ownership derives through conversation.owner. PostgreSQL transactions lock the parent conversation for mutations; identical POST preserves the existing timestamp, DELETE is idempotent. SQLite may reject concurrent writes with a controlled 503; no automatic retry.
- Only completed, nonblank assistant messages in non-deleted conversations are eligible. Archived conversations may be rated, consistent with editable owned history. Trashed conversations deny feedback mutation/read; restore recovers rating, permanent deletion/account deletion cascade. Export includes own rating when the flag is enabled, including trashed export. Disabled flag hides feedback metadata/controls, denies feedback endpoint. Ratings remain in the local DB until explicit deletion or parent purge.
- GET/POST/DELETE /api/ai/v1/conversations/<conversation UUID>/messages/<message UUID>/feedback/. POST JSON exactly {"rating":"like"} or {"rating":"dislike"}, 128-byte max. All successful responses 200 {"rating": "like"|"dislike"|null}. Invalid input 400; unauthenticated 401; CSRF 403; unknown/foreign/deleted/disabled 404; unsupported method 405; ineligible own message 409; database failure 503. Existing strict JSON parser and private/no-store used.
- History and export use one bounded feedback query per list (no N+1). If optional history feedback lookup fails, omit controls and retain history. Export failure is explicit 503. New responses gain assistant_message_id only when flag enabled and the durable completed message matches the displayed answer. Same metadata in JSON, grounded SSE, knowledge SSE and durable replay; cache/recovery remains authoritative and does not issue another model request. Older cache entries without identity safely show no rating controls until history reload.
- UI uses actual server UUID pair, localized FA/DE/EN tooltips, aria-pressed, minimum target size, same-origin CSRF fetch. Server-confirmed state; repeated click removes rating via DELETE. Pending requests disable both buttons; uncertain mutation result triggers GET reconciliation only, never automatic POST retry.

## Deployment boundary — IMPORTANT
Migration **ai_core.0006_message_feedback** adds a table and a foreign key only. It has not been applied to any live database. Local test migrations run on disposable databases. Do not deploy the new application code to an unmigrated runtime even with feedback flag OFF: Django's deletion collector may reference the new related table when deleting messages/conversations/users. Before either environment is released, establish a separately authorized schema-first or coordinated maintenance migration procedure compatible with existing deployment governance, verify exact DB identity, take a fresh backup and prove isolated restore, verify plan contains only 0006, and independently authorize migration, deployment and feature activation. Do not bypass guarded migration or release paths; no auto-migrate assumed. The previous application can run with the additive table present.
- Rollback: disable feedback flag (both layers); retain the table and existing feedback. Roll back application via the official owner-controlled path if required. Do not reverse migration or drop feedback data as part of routine rollback.
- No provider calls, real data access, configuration changes or operational migration are authorized by this PR.

## Test plan
Security, strict input, owner isolation, authentication/CSRF, eligible states, persistence and cascade, history/export query count, model/DB constraint, concurrent PostgreSQL writes and delete, JSON/SSE/recovery identity, failure paths, flag-off regression, JS state and same-origin/CSRF. Test real provider paths only with synthetic doubles in isolated network. Official CI/security and quality checks required before independent merge approval.
