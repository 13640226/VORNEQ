# Observability Foundation — VORNEQ

This document records the V1 observability baseline. It adds operational visibility without changing product, trust, verification, evidence, reputation, entitlement, or search semantics.

## Structured logging

VORNEQ uses `structlog` with the Python standard logging pipeline. Console logs are JSON and include an ISO timestamp, log level, logger name, and structured event fields.

Request logs include:

- correlation ID
- HTTP method
- request path
- status code
- duration in milliseconds
- database query count executed during the request

Credentials, request bodies, cookies, authorization headers, and user identifiers are intentionally not logged by the request middleware.

## Correlation IDs

Every HTTP response includes `X-Correlation-ID`.

A caller-provided ID is accepted only when it matches a conservative ASCII allowlist (`A-Z`, `a-z`, digits, `.`, `_`, `-`) and is at most 128 characters. Invalid or missing values are replaced with a UUID generated by VORNEQ.

## Prometheus metrics

`django-prometheus` exposes request/response metrics at `/metrics` and provides latency/error/request counters. VORNEQ additionally exports:

- `vorneq_db_queries_total{alias=...}` — database queries executed during HTTP requests

`PROMETHEUS_EXPORT_MIGRATIONS` is disabled to keep the first baseline focused on runtime service behavior.

Production ingress should restrict `/metrics` to the monitoring network or an authenticated proxy. The application endpoint itself intentionally stays compatible with standard Prometheus scraping.

## Health checks

`/health/` remains a read-only readiness endpoint. It checks:

- database connectivity using `SELECT 1`
- default storage reachability using `exists()`
- cache reachability using `get()`

The response also includes total check duration and `VORNEQ_RELEASE` when provided by the deployment environment. Failures return HTTP 503 without exposing exception details to clients.

## Deferred integrations

OpenTelemetry tracing and Sentry are intentionally not dependencies of this PR. They should be added only when VORNEQ has a concrete collector/exporter or Sentry project configuration, sampling policy, retention policy, and operational owner.

Grafana dashboards and alert thresholds are also separate follow-up work.
